# WhyStuck — Competitive Landscape & Go-to-Market Research

*Prepared July 2026. WhyStuck is a local, zero-telemetry MCP server for Claude Code / Codex / Cursor that diagnoses why repeated coding-agent loops/workflows fail and proposes reversible fixes (patches to skills, verifier rubrics, retry policies, stop conditions) for the user to approve. All traces stay on the user's machine. The name nods to GEPA (Genetic-Pareto reflective prompt evolution), [arXiv 2507.19457](https://arxiv.org/abs/2507.19457).*

### 1.2 The GEPA / DSPy optimization lineage (WhyStuck's namesake ancestry)

- **GEPA** (arXiv [2507.19457](https://arxiv.org/abs/2507.19457), accepted ICLR 2026 Oral): "Given any AI system containing one or more LLM prompts, GEPA samples trajectories... and reflects on them in natural language to diagnose problems, propose and test prompt updates, and combine complementary lessons from the Pareto frontier of its own attempts" (verbatim abstract, verified by direct fetch). Headline numbers: outperforms GRPO by an average Δ ≈ 6%, up to 20%, using up to **35× fewer rollouts**; outperforms MIPROv2 by >10% on average, +12% on AIME-2025.
- **`dspy.GEPA`**: an official first-class DSPy optimizer wrapping the reference `gepa-ai/gepa` implementation ([docs](https://dspy.ai/api/optimizers/GEPA/overview/)). Invocation: `gepa = dspy.GEPA(metric=metric, reflection_lm=reflection_lm); optimized_program = gepa.compile(student, trainset=trainset, valset=valset)`. DSPy itself: ★ ≈36.2k, MIT, Stanford NLP ([GitHub](https://github.com/stanfordnlp/dspy)).
- **Adjacent reflective-optimization tools** — all local libraries, none coding-agent-loop-specific: **TextGrad** (arXiv [2406.07496](https://arxiv.org/abs/2406.07496), "automatic differentiation via text," published in *Nature*), **Trace** (Microsoft Research, [GitHub](https://github.com/microsoft/Trace), MIT, generalizes TextGrad via an "Optimization with Trace Oracle" formalism), **MIPROv2** (arXiv [2406.11695](https://arxiv.org/abs/2406.11695), Bayesian search over instructions + demos, scalar-reward only, GEPA's benchmark baseline), **OPRO** (DeepMind, arXiv [2309.03409](https://arxiv.org/abs/2309.03409), "LLM as optimizer"), **PromptBreeder** (arXiv [2309.16797](https://arxiv.org/abs/2309.16797), self-referential evolutionary optimizer, research-only, no shipped package found).
- **Naming check**: the exact string "WhyStuck" returns no hits anywhere searched — clear to use. "GEPA" itself is an active OSS name (`gepa-ai/gepa`, plus forks `CerebrasResearch/gepa`, `SuperagenticAI/gepa-eval`) with no trademark registration found — WhyStuck reads as a direct, intentional nod rather than a collision.

## 2. Similarities & Overlap

WhyStuck sits at the intersection of three lineages, and should own that framing explicitly rather than let others draw the comparison first:

1. **Trace-based repeated-failure clustering** (shared with Latitude and Perseval): sample execution trajectories, detect repeated failure *signatures*, rank by frequency/severity. WhyStuck should credit this lineage in its docs ("inspired by the failure-clustering approach in tools like Latitude/Perseval") while drawing the line sharply: those tools instrument *production agents already shipped to users*; WhyStuck instruments *your own coding-agent session, on your own machine, while you're still developing*.
2. **Reflective natural-language optimization** (directly inherited from GEPA/DSPy, and shared conceptually with TextGrad/Trace/OPRO/PromptBreeder): sample trajectory → reflect in natural language → propose a targeted textual mutation → Pareto-select survivors. WhyStuck's novelty is applying this exact mechanism to skill files, verifier rubrics, retry policies, and stop conditions — the operating rules of a coding agent — rather than to a DSPy program's prompts or a general compound-AI pipeline.
3. **Local-first, zero-telemetry positioning** (shared with Perseval in this category, and with Ollama/LM Studio/Plausible/Umami/Obsidian/Tailscale outside it): a proven, actively-sought market position, not a niche nobody wants.

**How to differentiate sharply, in every piece of copy:**
- Lead with scope, not mechanism: "diagnoses *your own* Claude Code/Cursor/Codex session" vs. "observes production agents you've shipped."
- Name the one real overlap (Latitude) directly and contrast the trust model: Latitude auto-dispatches a coding agent to open a PR against your *production* code; WhyStuck proposes a specific, reversible edit to *its own operating rules* (a skill, a rubric, a retry policy, a stop condition) that you must approve before anything changes. This is a materially different risk profile and should be stated as such, not implied.
- Name Perseval directly too, since it is the closest local-first analog: "Perseval tells you a failure recurred and helps you write a regression eval for it. WhyStuck tells you *why* it recurred at the policy level and proposes the specific rule change — reversibly, pending your approval."
- Anchor "zero-telemetry" concretely, the way Perseval and LM Studio do: state exactly *where* data lives (a local SQLite/DuckDB file, a local log directory) and that there is *no server to send it to even if you wanted to* — this is a stronger claim than "we don't collect data," which cloud tools can also (falsely or truthfully) claim.

## 3. Drawbacks of Incumbents

- **No true local/zero-infra mode anywhere in the observability category.** Even "self-host" options (Langfuse, Helicone, Traceloop, Arize Phoenix) require running a server — Docker, a database, an OTel collector — before any signal appears. That is a categorically heavier lift than an MCP server that activates the moment it's added to `mcp.json`.
- **Pricing cliffs before value is proven.** Paid tiers start at $29–249/mo (Langfuse Core $29, Helicone Pro $79, Latitude Pro $99, Braintrust Pro $249) — real friction for a solo developer who just wants to understand why their *own* coding session looped, not a team standing up production monitoring.
- **Production-app mental model mismatch.** Every one of the nine core incumbents is built around traces = production API requests from a shipped application. Their dashboards, eval workflows, and pricing units (per-span, per-trace, per-seat) don't map onto "why did my own Claude Code session retry the same failing test six times."
- **Latitude, the closest analog, removes the human-approval step where it matters most.** It auto-dispatches a coding agent to open a PR fixing detected failure patterns — appropriate for production incident response, but not a model you want for changes to your *own* coding assistant's behavior, where a bad "fix" can compound into worse agent behavior.
- **Perseval, the closest local-first analog, stops short of a fix.** Its own FAQ states plainly that eval execution — let alone policy/prompt changes — is "on the roadmap," not shipped. The diagnosis-to-fix loop is open even in the product architecturally closest to WhyStuck.
- **Setup and time-to-first-insight.** SDK instrumentation, OTel exporters, and server provisioning are required across the incumbent set before a developer sees anything — versus a local MCP server that should surface a diagnosis on the very first re-run of a looping session.

## 4. Good Practices to Copy

- **Radically transparent, numbered free tiers on one page.** Langfuse, Latitude, Helicone, and Traceloop all put exact numbers (50K units/mo, 20K credits/mo, 10K requests/mo, 50K spans/mo) directly on a public pricing page rather than "contact sales" — copy this even though WhyStuck (as local OSS) may not need a paid tier at all; the *transparency norm* itself builds trust.
- **State the "core is fully open" boundary explicitly.** Langfuse lists exactly which enterprise features (SCIM, audit logs, RBAC) sit outside its MIT core, rather than leaving OSS-vs-paid ambiguous. For WhyStuck, this means being explicit in the README about what's in v1 vs. roadmap, mirroring Perseval's honest "on the roadmap" framing rather than overclaiming.
- **One-command self-host as a trust signal.** Laminar's `docker compose up -d` and its plain-language pitch ("Understand why your AI agent breaks. Iterate fast to fix it.") show that removing setup friction *is* the marketing message for a dev tool — WhyStuck's install bar should be `uvx whystuck` / `npx whystuck`, one line, no signup.
- **Put the privacy claim in the first sentence, not the FAQ.** Plausible ("No cookies, just insights"), Umami ("Your analytics data never leaves your servers"), LM Studio ("nothing leaves your machine unless you deliberately configure it to"), Obsidian ("No one else can read them, not even us"), and Tailscale ("We don't want your data") all lead with this claim as line one of their homepage. Perseval's line is the best template for WhyStuck specifically: a three-part negative-space claim — "No per-seat pricing, no data leaving your laptop, no procurement meeting."
- **Write tool descriptions and README content once, well — it compounds.** Glama grades every MCP server A–F, weighted 70% on per-tool description quality (purpose clarity, parameter semantics, conciseness) and 40%-weighted on the *minimum* tool score, meaning one badly-described tool drags the whole grade down. Since mcp.directory and Glama both auto-discover from the same official registry metadata, writing precise tool descriptions once pays off across every surface that inherits them.
- **Make the contribution bar to community lists mechanically obvious.** `punkpeye/awesome-mcp-servers`'s CONTRIBUTING.md is a one-paragraph, unambiguous spec: alphabetical order within category, one line per server, match existing formatting — copy this level of precision in WhyStuck's own docs for anyone who wants to contribute a diagnosis rule or skill-patch template.
- **Engage skeptical top comments openly rather than defensively.** The Show HN example for a local Claude Code CLI tool drew a top comment suggesting a competing tool was simply better — the post still reached 69 points/44 comments, because pushback engaged with rather than ignored doesn't kill a launch.

## 5. Promotion / GTM Playbook

This is sequenced for a solo developer with no marketing budget, no paid hunts, and no team to spread launch load across. Assets are listed with each step because most failed launches skip an asset, not a channel.

### Phase 0 — Before touching any channel (no fixed date, just a gate)
- **Working one-command install** (`uvx whystuck` or `npx whystuck`) — HN's own Show HN guideline is explicit: *"Show HN is for something you've made that other people can play with"* ([guidelines](https://news.ycombinator.com/showhn.html)). A broken or multi-step install kills every channel below simultaneously.
- **A demo GIF** showing an actual loop being diagnosed and a proposed patch being approved — every structural-pattern source found for X/Twitter and Show HN emphasizes visual proof over prose.
- **README leading with the privacy claim**, per §4, and an explicit comparison line naming Latitude/Perseval so the first HN/Reddit comment ("isn't this just X?") is already pre-empted in the README itself.
- Pitfall to avoid: do not open any social channel before this gate is met — an early low-effort post that gets buried is worse than no post, since HN/Reddit/PH all penalize (via ranking or community memory) a second post about the same unchanged thing shortly after a flop.

### Phase 1 — Discovery infrastructure (do this *before* Phase 2, ideally 3–7 days ahead)
Sequenced so that a curious clicker from any later social post lands in a populated ecosystem, not a lonely GitHub repo — and because several of these auto-propagate into each other.

1. **Official MCP Registry** (`registry.modelcontextprotocol.io`, currently in preview, backed by Anthropic/GitHub/PulseMCP/Microsoft — [about](https://modelcontextprotocol.io/registry/about)). This is the metadata source of truth other directories pull from — do this first. Process: add an `mcpName` field to `package.json`, publish to npm/PyPI, install `mcp-publisher`, run `mcp-publisher init` → edit `server.json` → `mcp-publisher login github` (GitHub Device Flow, ties the namespace to your verified GitHub identity) → `mcp-publisher publish` ([quickstart](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/quickstart.mdx)).
2. **mcp.directory** and **Glama** (glama.ai/mcp/servers) both auto-discover from the registry — check that the auto-pulled listing appeared, then email to "claim" the mcp.directory listing for a verified badge ([submit](https://mcp.directory/submit)). On Glama, write tight, example-driven tool descriptions *before* this step, since its A–F score is 70%-weighted on exactly that.
3. **Smithery**: `npx @smithery/cli` → `smithery mcp publish <url> -n <org>/whystuck` ([CLI docs](https://smithery.ai/docs/concepts/cli)). No verified install-count/leaderboard mechanic found — don't claim rankings you can't back up.
4. **`punkpeye/awesome-mcp-servers`** (90,986 ★, the single largest discovery surface found): fork, add one alphabetically-ordered line under the correct category matching existing formatting, open a PR ([CONTRIBUTING](https://github.com/punkpeye/awesome-mcp-servers/blob/main/CONTRIBUTING.md)). If submitting via an automated PR agent, appending `🤖🤖🤖` to the PR title opts into a fast-tracked merge.
5. **Claude Code plugin marketplace**: only relevant once WhyStuck is packaged as a plugin (`.claude-plugin/plugin.json` + `.mcp.json`), not as a bare MCP server. Test locally first (`claude --plugin-dir ./your-plugin`, `claude plugin validate ./your-plugin`), then submit to the community marketplace at **`clau.de/plugin-directory-submission`** (verified — the `anthropics/claude-plugins-community` repo's own description points here; this supersedes any older `platform.claude.com/plugins/submit` reference). Review "typically takes a few days," and the public catalog syncs nightly after approval — factor that lag into your launch-day timing. The separate `claude-plugins-official` marketplace is curated entirely at Anthropic's discretion; there is no application path into it.

## 6. Metrics & Timing

**Day of week for Show HN** — the data conflicts, so pick deliberately rather than defaulting to Monday or Friday:
- Myriade's analysis of **157,000+ Show HN posts since 2009** found Sunday has an **11.75%** "breakout" rate (≥30 votes) vs. **9.45–9.90%** on weekdays, with a peak hour of 12:00 UTC and a golden window of 11:00–16:00 UTC — concluding weekends are **20–30% more effective** for front-page odds, likely due to lower same-day competition ([Myriade](https://www.myriade.ai/blogs/when-is-it-the-best-time-to-post-on-show-hn)).
- Syften's community-experience guide argues the opposite framing — no magic hour, title/topic fit matters more — and defaults to a **weekday morning, 9am–12pm Eastern**, favoring raw audience size over low competition ([syften](https://syften.com/blog/hacker-news-marketing/)).
- Recommendation: if the goal is maximum front-page probability with a genuinely novel niche tool, Sunday is defensible. If the goal is maximum absolute reach and follow-on Twitter/Reddit amplification the same day, a Tuesday–Thursday morning is the safer default — pick one and don't split the difference by launching Monday or Friday, which both underperform in every source found.
- **Product Hunt** direction is directionally consistent: Tuesday–Thursday for maximum raw traffic, Friday–Sunday for an easier path to a "#1 Product of the Day" badge due to lower same-day competition ([smollaunch](https://smollaunch.com/guides/launching-on-product-hunt) — marketing-blog source, treat as directional, not primary data).

**Sequencing relative to assets** — launch only after, in this order: (1) working one-command install, (2) demo GIF, (3) README with the privacy-first-sentence pattern and an explicit Latitude/Perseval comparison, (4) Phase 1 discovery-infrastructure listings live (registry → directories → awesome-list PR). Do not run Phase 2 (Show HN/X) before Phase 1 is live — a clicker who checks "is this real" via a directory search should find it already indexed.

**What "good" looks like in week 1** (calibrated against the real analogs found, not aspirational round numbers):
- Show HN: **50–150 points, 40–90 comments** is a strong outcome for a solo-dev local Claude Code tool — both real comparables found landed in or near this band (138 pts/85 comments; 69 pts/44 comments).
- Product Hunt: a **top-5-of-day** placement is a realistic strong outcome for a well-executed niche launch; **#2 Product of the Day** is the ceiling seen in the one directly comparable MCP-ecosystem launch found (mcp-use, 586 upvotes).
- GitHub: triple-digit stars (low hundreds) within the first week is a reasonable bar for a solo project matching the Show HN comparables' traction — treat anything in the thousands in week 1 as exceptional, not a baseline expectation.
- Directory presence: confirmed live listings on the official MCP registry, mcp.directory, Glama, and Smithery, plus a merged PR on `awesome-mcp-servers` — these are binary, verifiable, and fully within your control regardless of how the social channels perform.

**How directory listings compound:** publishing once to `registry.modelcontextprotocol.io` is the single highest-leverage discovery action because both mcp.directory and Glama explicitly auto-discover from that same registry — one action feeds multiple downstream listings without repeated manual work. Glama's A–F grading (70% weighted on per-tool description quality, with the *minimum* tool score dragging the whole grade down 40%-weighted) means the quality bar you clear once in your tool descriptions and README propagates into every surface that reuses that same metadata, compounding the value of getting the documentation right before Phase 1 rather than after.
